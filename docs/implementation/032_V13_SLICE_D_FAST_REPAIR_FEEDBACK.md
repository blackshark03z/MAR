## 1. Problem and baseline

The existing authoritative verifier executed every command in a verification profile even after an earlier command had already failed. Historical MAR evidence summarized in the V1.3 roadmap shows failed `go-standard` runs spending roughly 29.5–32.1 seconds on `vet + build` after `go test` had already failed. That delayed the next useful repair cognition turn without improving the failed candidate's eligibility for integration.

Slice D keeps the authoritative verification model and changes only the failed-candidate feedback path.

## 2. Design

The verifier remains a single ordered authoritative pass.

For an all-pass candidate, the all-pass authoritative profile executes every command exactly once. There is no duplicate preflight verification pass and no fast path that can independently produce VERIFIED.

For a concrete verification command failure, the verifier now records the first failed command evidence and stops executing later commands in that profile. The existing durable `VerificationEvidence` remains the source of truth. A command-failed result is persisted as `VERIFICATION_FAILED` and transitions the task to `RETRY_WAIT`, allowing the existing recovery/replacement-attempt lifecycle to continue only after physical termination authority is resolved.

acceptance-only failure remains BLOCKED. An unverified acceptance outcome remains BLOCKED. Only a concrete failed verification command uses the automatic repair path.

## 3. Repair-context continuity

The next cognition attempt receives bounded failure context through the existing DecisionProjection. The derived `first_failed_command` contains:

- command index;
- command name;
- arguments;
- working directory;
- exit code;
- duration;
- output SHA-256;
- bounded output prefix.

repair feedback is reconstructed from MAR durable evidence. It is derived from the same persisted `VerificationEvidence`; no second durable event store, transcript replay requirement, or provider-native memory authority is introduced.

The first replacement cognition turn can therefore see the material failure immediately from current MAR durable state.

## 4. Controlled evidence

The focused verifier regression uses a three-command profile:

1. `go test ./...` — fails;
2. `go vet ./...` — would pass if executed;
3. `go build ./...` — would pass if executed.

Observed Slice D behavior: only command 1 executes. The failed command evidence is persisted, later authoritative commands were not executed after the first failure, and task state becomes `RETRY_WAIT` rather than an integration-eligible state.

Controlled command work therefore changes from 3 command invocations to 1, a reduction of 2/3 = 66.7% for this early-fail fixture. This is the measured repair-feedback improvement for the bounded implementation.

Historical evidence from the canonical V1.3 roadmap indicates the corresponding real `go-standard` opportunity was roughly 29.5–32.1 seconds of `vet + build` work after an already-failed `go test`. That historical range is supporting baseline evidence, not a new wall-clock benchmark generated by this recovery task.

## 5. All-pass and final-verification invariants

The all-pass regression confirms the all-pass authoritative profile executes every command exactly once.

final VERIFIED semantics are unchanged. A candidate can become VERIFIED only after the complete authoritative profile passes, criterion-specific acceptance evaluation succeeds, environment/candidate identity remains valid, and the existing revision-bound evidence persistence succeeds. Integration remains serialized behind VERIFIED evidence exactly as before.

Repair feedback is explicitly non-authoritative. A command failure produces `VERIFICATION_FAILED`; it cannot produce `VERIFIED`, `READY_TO_INTEGRATE`, `INTEGRATING`, or `COMPLETE` from that failed outcome.

- one early `break` in the existing verifier command loop;
