# Slice 013 — Semantic Checkpoint + Resume

**Status:** IMPLEMENTED / VERIFIED

**Frozen architecture source:** MAR V1 Resource & Reliability Model sections 7, 10 and 14; execution-attempt fencing; bounded context architecture.

## Goal

Persist the minimum semantic worker state needed to reconstruct a new bounded model session after worker interruption without replaying the full model/tool transcript.

Checkpoint state is durable recovery memory, not authority. The immutable Goal Contract and current MAR state remain authoritative.

## Durable checkpoint model

`internal/domain/checkpoint.go`

A semantic checkpoint records:

- Goal Contract hash;
- base revision;
- current revision;
- completed work;
- current hypothesis;
- changed areas;
- verification status;
- blockers;
- remaining work;
- next action;
- critical evidence references;
- task/attempt/run_epoch identity;
- monotonically increasing task-local version;
- creation time;
- SHA-256 integrity digest.

The integrity digest covers all immutable checkpoint identity and semantic fields except the digest itself.

Checkpoint payload validation requires a current hypothesis, verification status and next action. The service also enforces a 64 KiB serialized semantic-payload bound.

## SQLite persistence

`internal/store/sqlite.go`
`internal/store/checkpoint.go`

Schema version 6 adds `semantic_checkpoints` with:

- immutable checkpoint primary key;
- task + attempt + run_epoch binding;
- unique `(task_id, version)`;
- Goal hash/base/current revision identity;
- serialized semantic payload;
- integrity hash;
- creation timestamp;
- task/attempt foreign keys.

Checkpoint publication runs inside one SQLite transaction under the existing single-authoritative-writer/WAL model.

Before allocation/insertion, the transaction validates that the referenced attempt is still the task's current ACTIVE `attempt_id/run_epoch`. A stale/logically fenced attempt therefore cannot publish a late checkpoint.

Versions are allocated monotonically inside the same transaction. There is no update API for an existing checkpoint snapshot.

## Latest-valid recovery selection

`LatestValidCheckpoint` reads newest-first and accepts a snapshot only when:

- attempt identity matches the persisted attempt record;
- checkpoint epoch is not from a future task epoch;
- Goal Contract hash matches durable task truth;
- base revision matches the immutable Goal Contract;
- payload decodes;
- timestamp parses;
- semantic fields validate;
- SHA-256 integrity digest matches.

Invalid/corrupt/incompatible newer snapshots are skipped. They never override an older valid checkpoint or durable task truth.

This selector intentionally permits a valid checkpoint from an earlier, physically terminated attempt so a replacement attempt can resume from it.

## Service contract

`internal/service/task_service.go`

`TaskService` exposes:

- `PublishCheckpoint(...)` — bounded semantic checkpoint publication;
- `LatestValidCheckpoint(...)` — latest compatible valid snapshot retrieval.

Checkpoint IDs remain randomly generated by MAR. Callers do not choose checkpoint version or Goal hash/base revision metadata.

## Agent checkpoint protocol

`internal/agent/loop.go`

Slice 013 adds the reserved synthetic tool `checkpoint_task`.

The model supplies only semantic recovery content:

- completed work;
- hypothesis;
- changed areas;
- verification status;
- blockers;
- remaining work;
- next action;
- critical evidence refs.

MAR supplies task/attempt/run_epoch, Goal hash/base revision, current revision, version, creation time and integrity hash.

`checkpoint_task` must be the sole tool call in its model turn. The loop revalidates durable attempt authority immediately before publishing it. A publish race that loses attempt authority terminates without allowing a stale checkpoint to become authoritative recovery memory.

The checkpoint tool is available even for a read-only Goal because it mutates only task-owned MAR recovery metadata, not project content.

## Bounded resume

At the beginning of a new agent run, after building fresh Slice 011 repository context, the loop requests the latest valid semantic checkpoint.

If one exists, MAR independently verifies its task/Goal/base/integrity identity and injects it into the new initial user message as:

`UNTRUSTED_DURABLE_SEMANTIC_CHECKPOINT_JSON`

Fresh repository evidence is separately included as:

`UNTRUSTED_REPOSITORY_CONTEXT_JSON`

The checkpoint is explicitly treated as **untrusted semantic task memory**, not authority or instructions. The Goal Contract remains authoritative and current repository/tool evidence wins over stale hypotheses.

The serialized resume checkpoint has its own hard agent byte limit (`MaxResumeBytes`) in addition to the overall model-request bound.

A replacement model session therefore starts from exactly the bounded initial session shape:

1. system/base instructions;
2. Goal Contract + latest valid semantic checkpoint (or null) + fresh bounded context.

Full transcript replay is not required or performed by Slice 013.

## Recovery / fencing relationship

Semantic checkpointing does not weaken physical recovery requirements.

For same-workspace mutable replacement:

1. old attempt is logically fenced;
2. previous mutation-capable process authority is confirmed terminated/revoked by existing Slice 003/010 mechanisms;
3. task returns to workspace-ready state;
4. replacement attempt advances run_epoch;
5. replacement agent loads latest valid checkpoint + fresh context.

The checkpoint itself never authorizes replacement execution.
